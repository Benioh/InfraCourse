# 术语表

本表只解释课程中会反复出现、且容易被误用的 infra 术语。第一次遇到术语时，先读“课程中怎么用”，再回到对应 lab 的源码和 notebook。

## 训练与显存

### MFU

Model FLOPs Utilization，近似衡量模型训练实际使用了理论算力的比例。课程中用于 L05 判断扩展实验是否只是“跑起来”，还是有效使用 GPU。MFU 低时先查 batch/seq_len、通信、数据加载、checkpoint、recompute，而不是只看 GPU 利用率。

### 激活显存

forward 中间结果为 backward 保留的显存。它通常随 `micro_batch_size × seq_len × hidden × layers` 增长，很多 OOM 并不是参数太大，而是激活太大。

### Activation Recompute

也叫 checkpointing/recompute，用额外计算换显存。课程中要求同时报告 peak memory 和 step time，因为重算不是免费优化。

### Distributed Optimizer

把 optimizer state 或梯度状态分片到多个 rank 的优化器策略。Megatron 中它会影响显存、通信和 checkpoint 语义，不能只按单卡 optimizer 理解。

## 分布式并行

### Rank / Local Rank / World Size

`RANK` 是全局进程编号，`LOCAL_RANK` 是本机 GPU/进程编号，`WORLD_SIZE` 是总进程数。L00/L01.5/L02 都要求把它们写进日志，避免 rank/device mismatch。

### Collective

多 rank 同步通信原语，例如 `all_reduce`、`broadcast`、`all_gather`、`barrier`。所有 rank 必须以兼容顺序进入 collective，否则常见结果是 hang。

### DDP

DistributedDataParallel。每个 rank 持有模型副本，backward 时同步梯度。课程中先用 L01.5 做 2-rank smoke，再在 L02 扩展到 TP/PP 沙盘。

### Tensor Parallel / TP

把同一层的矩阵或 attention 计算切到多个 rank。ColumnParallelLinear 与 RowParallelLinear 的切分维度不同，通信语义也不同。

### Pipeline Parallel / PP

把不同层放到不同 stage。microbatch 太少会产生 pipeline bubble；microbatch 太多又可能增加激活或调度开销。

### Pipeline Bubble

流水线 stage 等待其他 stage 的空档。L02/L05 中用 notebook 和 Megatron-shaped schedule 图计算 bubble fraction。

## 数据与 Checkpoint

### Indexed Dataset

Megatron 常用的 `.bin/.idx` 数据格式。`--data-path` 通常指向 prefix，而不是原始 `.jsonl` 文件。

### Tokenizer / Processor

把文本或多模态输入转换为模型张量的组件。checkpoint、tokenizer、processor 必须版本化，否则 resume/serving/RL rollout 可能语义漂移。

### Checkpoint Resume

从保存的模型、优化器、调度器、随机状态继续训练。课程报告必须说明恢复了哪些状态，不能只说“加载权重”。

## Serving

### KV Cache

保存 attention key/value，避免 decode 时重复计算历史 token。它的显存随 batch、上下文长度、层数、hidden 和并发变化。

### Prefill

处理完整 prompt 并生成首个可复用 KV cache 的阶段。长 prompt 通常先影响 TTFT。

### Decode

逐 token 生成阶段。decode 更容易暴露 KV cache 读取、调度、batch 组成和显存带宽瓶颈。

### TTFT

Time To First Token，从请求到首 token 返回的时间。TTFT 高时先拆 queue、tokenize、prefill、prefix cache，而不是笼统说“模型慢”。

### ITL / TPOT

Inter-token Latency / Time Per Output Token，decode 阶段相邻输出 token 的时间。ITL 高通常指向 decode 调度或 KV cache 读写问题。

### Prefix Cache

复用重复 prompt 前缀的 KV 结果。命中率低时先检查 prompt 模板、系统提示、采样参数和 cache key 是否稳定。

### PD 分离

Prefill/Decode disaggregation，把 prefill 与 decode 放到不同资源池。它只有在 workload 资源画像明显不同且路由成本可控时才有收益。

## RL 与 SLiME

### Rollout

用当前策略模型生成回答的过程。L10.5 单独训练 rollout-only smoke，是为了先隔离 serving/采样吞吐，再接 actor 更新。

### Reward

对生成结果的评分。课程中 reward parser 要有 self-test，避免“训练失败”其实是答案解析失败。

### KL

策略模型与参考模型输出分布差异的约束项。KL 过高可能说明策略漂移，过低可能说明学习停滞或 reward 无效。

### Actor / Rollout 拆分

SLiME 中训练 actor 与 SGLang rollout worker 的资源拆分。它会引入 Ray、weight sync、server 参数和 checkpoint 兼容性问题。

### Weight Sync

把 actor 新权重同步给 rollout 引擎。同步慢会拖垮 RL 吞吐，同步错会让 rollout 使用过期或不兼容权重。

## 报告与证据

### Validation-only

只验证配置、脚本路径、数据 schema 或 fallback 逻辑，没有真实 GPU/集群性能结论。报告必须显式标注，不能写成真实训练或 serving 成功。

### Evidence Path

支撑结论的文件路径，例如 `command.sh`、`config.resolved.yaml`、`metrics.jsonl`、日志、trace、checkpoint、dashboard。没有 evidence path 的结论只算猜测。

## 新增半关术语

### GPU 体系结构

- **HBM 带宽**：GPU 全局显存读写上限；L01.7 fused softmax 的主要收益来自减少 HBM 往返。
- **Occupancy**：SM 上活跃 warps/blocks 的比例；受寄存器、SMEM、BLOCK_SIZE、num_warps 共同限制。
- **SMEM**：shared memory，block 内线程共享的高速片上存储；BLOCK 过大可能让 occupancy 降低或 out-of-resource。

### 第四并行轴

- **Context Parallel (CP)**：沿序列维切分上下文，让长上下文 attention 的 KV 通过 ring 在 rank 间流动。
- **Ring Attention**：Q stationary、KV ring 的 attention 计算路径；通信量随 seq 增长，需与 activation 显存节省权衡。
- **Expert Parallel (EP)**：MoE 中把 expert 分到不同 rank；router dispatch 后通过 all-to-all 交换 token。
- **Top-k Router**：为每个 token 选择 k 个 expert 的路由器；负载不均会导致 collapse 或 overflow。
- **Capacity Factor**：每个 expert 接收 token 的容量倍率；太小会 drop token，太大浪费 padding/通信。
- **YaRN**：RoPE 长上下文外推的一类缩放方法；报告必须区分训练长度、目标长度与推理 scale。

### 量化与投机

- **AWQ**：按 group 保存 weight scale/zero 的 weight-only 量化路径；group_size 必须与 hidden/pack dim 对齐。
- **SmoothQuant**：用 activation 统计平滑 channel outlier，再调整 weight/activation scale。
- **FP8**：Hopper/H200 上常见的低精度格式；4090 路径只能做配置/数学验证，不声明真实 FP8 加速。
- **KV-cache 量化**：把 KV block 存成 int8/fp8 并保存 scale metadata，目标通常是省显存而非直接降 TTFT。
- **Acceptance Rate**：speculative decoding 中 draft token 被 target 接受的比例；它决定 speedup 是否覆盖 draft 成本。

### 数据工程

- **WebDataset Shard**：把样本打包成 tar shard 的数据组织方式，便于顺序读取、worker 切分和容灾。
- **Detshuffle**：确定性 shuffle，同 seed 下 shard/sample 顺序可复现。
- **MinHash + LSH**：近重复检测方法；必须用人工抽样校准阈值，避免短文本伪重复。

## v2 增量术语（系统级真实痛点）

### Train-Infer Mismatch · 训推不一致

- **训推不一致 (Training-Inference Mismatch)**：相同权重下 rollout engine（SGLang）与 training engine（Megatron / FSDP）对同一 token 序列计算的 log prob 不同。根因 = 浮点不结合 + decode/prefill 矩阵形状不同 → 不同 reduction kernel / Tensor Core 指令 → 累加顺序不同。dense 模型 K3 KL 通常 1e-5~1e-3，MoE 因为 router 选择不同 expert 可达 1e-1。
- **K3 KL**：Schulman 提出的 KL 估计器 $k_3 = \frac{p}{q} - 1 - \log\frac{p}{q}$。无偏 + 总是非负 + 方差最小，是现代 RL 监控训推不一致的工业标准。K1（log ratio）方差大可正可负，K2（log² ratio）总是非负但有偏。
- **TIS (Truncated Importance Sampling)**：把 ratio clip 到 [lower, upper]（mode='clip'）或越界设 0（mode='truncate'）。
- **MIS (Masked Importance Sampling)**：TIS clip + sequence-level **mask**（越界 token 不参与梯度）+ **veto**（rollout_logp < log(1e-6) 整条丢弃）。比单独 TIS 更稳，slime mismatch 实验中 token TIS only 崩溃，TIS + MIS + batch norm 不崩溃。
- **Geometric Sequence IS**：$\text{seq\_weight} = (\prod_{t} \text{ratio}_t)^{1/T}$，几何平均比累乘数值更稳，比 token 级有更多信号；长上下文友好（length-invariant）。
- **Veto Threshold**：rollout 概率阈值（例如 $10^{-6}$）。任一 token 概率低于此则整条序列丢弃，防止 ratio 爆炸到 1e9 量级污染梯度。
- **Self-Normalized IS / batch_normalize**：把 batch 内 IS weights 除以均值，让平均权重为 1，稳定有效学习率。

### CUDA IPC Weight Sync · 零拷贝权重同步

- **handle tuple**：`MultiprocessingSerializer.serialize(tensor)` 返回的元数据 bytes，包含 `(rebuild_fn, size, stride, dtype, device, CUDA IPC handle, refcount, event_handle, ...)`，**不含数据**。一个 [1024, 1024] fp32 tensor (4MB) 的 handle 通常 < 200 bytes。
- **CUDA IPC**：CUDA 提供的 inter-process 共享 GPU 内存机制。一个进程把 tensor 的 storage 注册成 IPC handle，另一个进程拿到 handle 后能直接映射到同一块 VRAM，无需复制数据。
- **`update_weights_from_tensor`**：SGLang 的接口，接收 `LocalSerializedTensor(values=[handle_bytes...])`，在每个 TP rank 反序列化得到与训练侧共享 storage 的 tensor，然后 `model.load_weights` 把指针换掉。
- **`update_weights_from_distributed`**：通过 NCCL 或 IB 在分离资源组之间传 tensor 数据本身，用于 disaggregate 策略。
- **`update_weights_from_disk`**：把权重写到下层存储再读上来；最简单但 I/O 是瓶颈；优势是 rollout 弹性扩缩容最容易（AReaL 选这条）。
- **flush_cache 时序**：weight update 会让 KV cache 失效；多 tensor 更新时只在最后一个 tensor 调 `flush_cache=True`，避免 radix tree 反复重建。
- **分桶更新 (bucketed update)**：slime 在大 MoE 模型上把参数分批 upload 到 GPU，避免完整 model weights 与 SGLang 并存导致 OOM。

### Multi-turn Chat Template · 多轮 tokenize / loss mask

- **fixed-base delta tokenization**：用稳定 BASE_CONVERSATION（system + user）作为前缀，每条 msg 单独算 delta = `apply_chat_template(BASE+[msg]) - apply_chat_template(BASE)`，再 tokenize delta，从而绕开三大模板暗坑。verl PR #1668 (Yanbin Jiang) 提出。
- **默认 system 注入**：Qwen2.5-Instruct 等模板的隐式行为——messages 起手不是 system 时自动塞默认 system message。它让"分段 tokenize 后拼接"和"整段 tokenize"的 token 序列不一致。
- **think token strip**：QwQ-32B / Qwen3 的模板会在 assistant 不是最后一条时自动删除 `<think>...</think>` 内容（推理优化）。但训练必须保留 think，否则模型学不到 reasoning chain。fixed-base 法把每条 assistant 都放在 BASE+[msg] 末尾，不会触发 strip。
- **`return_assistant_tokens_mask`**：HF tokenizer 的内置功能，要求 chat template 用 `{% generation %}` 关键字明确标记 assistant 段。绝大多数模型没标，所以不可依赖。
- **loss_mask 约定**：`-100` 表示该 token 不参与 loss（CrossEntropyLoss `ignore_index`），其它值是真实 token id。verl/TRL 都用这套约定。

### Memory Snapshot · 显存泄露归因

- **`torch.cuda.memory._record_memory_history(enabled='all')`**：开启 PyTorch 显存事件录制；记录每次 alloc/free + Python stack 回溯。
- **`torch.cuda.memory._dump_snapshot('snap.pickle')`**：把录制的事件 dump 为 pickle，可上传 https://pytorch.org/memory_viz 可视化。
- **按 top-of-stack frame 聚合**：把所有未 free 的 allocation 按 stack 最顶（leaf）frame 分组求和，定位真正泄露的函数。整条 stack 聚合在循环调用下会被拆成多个 entry，归因失效。
- **closure capture leak**：典型 PyTorch 泄露——`register_forward_hook(lambda x: ...)` 闭包了大 tensor，hook 不 remove 则 tensor 永远 free 不掉。VLM RL 训练 50 step 涨 50 MB 的常见原因。

### CUDA Graph · 消除 CPU launch 开销

- **CUDA Graph capture/replay**：录制一段 kernel launch 序列 + buffer 指针；replay 时 GPU 用预录指针读写，CPU 几乎零开销。decode 一次 1 token 时 CPU bubble 占比能到 30%+，graph 直接消除。
- **static buffer 复用**：graph 内部记录的是 buffer 虚拟地址；replay 时必须 `copy_` 把新输入写进同一块 input buffer，不能新 alloc，否则地址变了 graph 失效。
- **多 batch size graph cache**：decode 的 bs 会变（pad to power-of-2），需为每个常见 bs 各 capture 一个 graph。SGLang `cuda_graph_max_bs` / `cuda_graph_bs` 就是这个意思。
- **Memory Savor (`torch_memory_saver`)**：用 CUDA Virtual Memory 让物理页可"暂停"——`pause()` unmap 物理页保留虚拟地址；`resume()` 重新 map。所有指针包括 graph 内部的都仍然有效。
- **为什么不能用 cudaFree**：cudaFree 释放后虚拟地址失效，captured graph 内部的 buffer 指针指向悬空内存，graph 立即废掉。

### Chunked GAE · 长上下文 RL 100-300× 加速

- **GAE 反向递推**：$A_t = \delta_t + \gamma\lambda A_{t+1}$，naive 实现是 O(T) 严格串行的。在长上下文（T=32K+）RL 中是 CPU bottleneck。
- **Chunked GAE**：把序列切成 chunk_size 长度的 chunks，chunk 内部仍反向递推，chunk 之间通过单个标量 boundary correction 传递。算法 / 浮点运算次数都不变，但 32K 串行 → 64 串行 + 512 并行。
- **boundary correction**：本 chunk 末尾 token 的"下一步 advantage"取自下一 chunk 起点的 advantage，这一个标量足以让所有 chunk 输出与 naive 数学等价。
- **slime batch-GAE 实测加速**：长 T RL 上 100-300×（来源：[ppo-gae-chunk.md](../github_repo/Awesome-ML-SYS-Tutorial/rlhf/slime/batch-GAE/ppo-gae-chunk.md)）。

### Co-locate vs Disaggregate · RL Placement

- **Co-locate**：训练与推理同卡，时分复用，必须 offload/upload 显存（memory savor）。verl FSDP+SGLang、slime Megatron+SGLang 走这条。优势：单集群、低延迟。劣势：DP attention 等很多优化没法启用。
- **Disaggregate**：训练集群 + 推理集群分离并发跑。AReaL、OpenRLHF (部分配置) 走这条。优势：rollout 弹性扩缩、DP 优化空间大。劣势：跨集群 NCCL/IB 通讯。
- **Multi-stage Wake Up**：verl co-locate 下精细控制 SGLang `mem static fraction` 的机制，避免与 megatron weights 同时常驻 GPU 时 OOM。slime 用分桶更新+精细 offload 也能达到类似效果。
