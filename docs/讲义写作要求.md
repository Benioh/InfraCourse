# AI Infra 技术讲义写作要求

你要写的是一节“ AI Infra 技术课”的讲义，不是宣传稿、博客、论文综述或大模型生成的泛泛科普。讲义的目标是帮助学生理解一个具体技术问题、掌握核心机制、看懂工程实现，并能在课后复现或继续学习。

> 批量重构课程时，先读 [课程重构执行规范](课程重构执行规范.md)。该规范以 `labs/l20_vllm_scheduler_kv` 为样板，规定了 `lecture.md`、`system_map.md`、`source_walkthrough.md`、`outputs/`、`quests/*.yaml` 和 `quiz.yaml` 的落地格式。

## 1. 写作定位

讲义应具备以下特征：

1. **教学性**
   - 讲义要服务于课堂教学。
   - 每一节内容都应回答：学生为什么需要学这个？学完能解决什么问题？
   - 不要堆概念，要按“问题 → 背景 → 机制 → 实现 → 局限 → 小结”的顺序展开。

2. **工程性**
   - AI Infra 技术课必须体现真实工程问题。
   - 不能只讲抽象原理，要说明它在训练、推理、部署、性能优化或系统设计中的作用。
   - 涉及 vLLM、SGLang、KV Cache、Continuous Batching、Tensor Parallel、Pipeline Parallel、ZeRO、Megatron、Ray、Kubernetes 等内容时，要说明它们解决的具体瓶颈。

3. **可解释性**
   - 每个关键概念都要用清楚的定义解释。
   - 定义之后必须给出直观解释、典型场景和容易误解的地方。
   - 不要只写“提升效率”“增强性能”“优化资源利用”，必须说明具体提升在哪里、为什么能提升、代价是什么。

4. **可复现性**
   - 如果涉及命令、配置、代码或实验，应尽量给出可执行的最小示例。
   - 所有参数、输入、输出、前置条件都要写清楚。
   - 不要写“配置好环境后运行即可”这种空话。

5. **层次感**
   - 内容要从简单到复杂。
   - 先讲概念，再讲机制，再讲实现，再讲优化。
   - 不要一上来就堆大量缩写和系统名。

6. **边界感**
   - 要明确说明某个技术适合什么场景，不适合什么场景。
   - 不要把任何技术写成万能方案。
   - 对性能优化类内容，必须说明约束条件，例如 batch size、context length、GPU 显存、网络带宽、模型大小、并发数等。

### 1. 问题背景

从具体问题切入，而不是从宏大叙述切入。

推荐写法：

> 在大模型推理中，同一个请求通常包含两个阶段：prefill 和 decode。prefill 阶段需要处理完整 prompt，计算量主要由输入长度决定；decode 阶段每次只生成一个 token，但会重复访问历史上下文。因此，当并发请求增多时，系统瓶颈往往不只是模型计算本身，还包括 KV Cache 显存占用、调度策略和 batch 组织方式。

避免写法：

> 随着人工智能技术的快速发展，大模型已经成为推动产业智能化升级的重要引擎。为了满足日益增长的推理需求，AI Infra 技术变得越来越重要。

禁止使用这种泛泛开头。

#### KV Cache

**定义：**
KV Cache 是自回归 Transformer 推理过程中缓存历史 token 的 Key 和 Value 张量的一种机制。它避免模型在生成每个新 token 时重复计算之前所有 token 的注意力投影。

**直观理解：**
可以把 KV Cache 理解为模型对历史上下文的“中间计算结果缓存”。没有 KV Cache 时，每生成一个 token 都要重新处理整个历史序列；有了 KV Cache 后，模型只需要处理新 token，并复用之前保存的 Key 和 Value。

**为什么重要：**
KV Cache 能显著降低 decode 阶段的重复计算，但会带来额外显存占用。上下文越长、batch 越大、模型层数越多，KV Cache 占用越明显。

**常见误解：**
- KV Cache 不是文本缓存，而是注意力层中的张量缓存。
- KV Cache 减少的是重复计算，不是减少模型参数量。
- KV Cache 提升 decode 效率，但会增加显存压力。

### 6. 性能分析要求

AI Infra 讲义中，凡是出现“更快”“更省显存”“吞吐更高”“延迟更低”，必须说明：

推荐写法：

```md
Continuous batching 提高吞吐的原因不是单个请求变快，而是调度器可以把不同请求在 decode 阶段动态合并，从而减少 GPU 空转。它主要改善系统整体吞吐，但单个请求的端到端延迟不一定总是降低。在高并发场景下，这种调度方式通常更有价值；在低并发或严格低延迟场景下，收益可能不明显。

KV Cache 的显存占用可以粗略估算为：

KV memory ≈ 2 × L × B × S × H × D × bytes

其中，2 表示 Key 和 Value 两组张量，L 是层数，B 是 batch size，S 是序列长度，H 是注意力头数，D 是每个头的维度，bytes 是每个元素占用的字节数。

## 14. 语言生动性要求

讲义的语言要清楚、具体、有现场感。不要写成冷冰冰的百科条目，也不要写成宣传文案。理想风格是：一位有经验的技术老师正在给学生讲一个真实工程问题，语言自然，解释充分，例子具体。

### 14.1 生动但不口水化

语言可以适当生动，但不能变成闲聊、鸡汤或段子。

推荐风格：

> 可以把 prefill 理解为“先把整段 prompt 读一遍并建立上下文”，而 decode 则像“每次只往后写一个字，但写的时候要不断回头看前面已经写过的内容”。因此，prefill 更像一次大批量计算，decode 更像一个频繁访问历史记录的逐步生成过程。

避免风格：

> Prefill 就像大脑飞速运转，decode 就像灵感源源不断地冒出来。

后者不准确，也不适合技术讲义。

---

### 14.2 讲清楚“为什么”，不要只给结论

每讲一个技术点，都要尽量补上它背后的动机。

差：

> KV Cache 可以提升推理效率。

好：

> 在没有 KV Cache 的情况下，模型每生成一个新 token，都要重新处理前面所有 token。这样历史越长，重复计算越多。KV Cache 的作用就是把前面已经算好的 Key 和 Value 保存下来，下一步生成时直接复用，所以 decode 阶段不需要反复重算完整上下文。

更好的讲法是先让学生感受到问题：

> 假设用户输入了 2000 个 token，模型已经生成了 100 个 token。现在它要生成第 101 个 token。如果每一步都重新计算前面 2100 个 token，很多计算其实是在重复做同一件事。KV Cache 就是为了解决这个重复计算问题。

---

### 14.3 多用“具体场景”解释抽象概念

不要只讲定义。每个重要概念都要尽量放到一个真实场景里。

例如讲 Continuous Batching：

差：

> Continuous Batching 是一种动态批处理机制，可以提升大模型推理吞吐。

好：

> 普通 batching 像是一辆车必须等所有乘客一起上车、一起下车。问题是，大模型推理中的请求长度不同，有的用户 prompt 很短，有的很长，有的生成 20 个 token，有的生成 1000 个 token。如果仍然要求一个 batch 里的请求同步推进，短请求会被长请求拖住。Continuous Batching 的思路是：谁完成了就先离开，新的请求可以及时补进来，让 GPU 尽量不要空着。

但要注意：类比之后必须回到技术本身：

> 对应到推理系统中，这意味着调度器会在 decode 过程中不断维护一组活跃请求，把仍在生成的请求和新来的请求重新组织成 batch，从而提高整体吞吐。

---

### 14.4 使用“先直观、后精确”的解释顺序

复杂概念不要一上来就给正式定义。建议顺序是：

1. 先说它解决什么问题。
2. 再用直观语言解释它在做什么。
3. 然后给出准确技术定义。
4. 最后说明工程代价和适用边界。

示例：

```md
为什么需要 Tensor Parallel？

当模型太大时，单张 GPU 放不下完整参数，或者即使能放下，单卡计算也太慢。Tensor Parallel 的思路是把同一层里的大矩阵计算切开，让多张 GPU 一起算。

更具体地说，Tensor Parallel 不是把不同数据样本分给不同 GPU，而是把模型内部的某些矩阵乘法切分到多张 GPU 上。例如一个很大的线性层可以按列切分或按行切分，不同 GPU 计算不同部分，最后再通过通信把结果合并。

它的好处是降低单卡显存压力，并提高单层计算并行度。代价是每一层内部都会引入跨卡通信，因此它非常依赖 NVLink、InfiniBand 这类高速互联。
14.5 句子要有信息密度，但不要压缩得太硬

不要写成论文式长句，也不要写成短视频口播。每句话尽量只表达一个明确意思。

差：

通过对请求调度、缓存管理和计算图执行进行联合优化，现代推理框架能够在复杂异构环境下实现面向多场景的高效部署。

好：

现代推理框架通常同时优化三件事：请求怎么排队，KV Cache 怎么管理，GPU kernel 怎么执行。请求调度影响吞吐，缓存管理影响显存，kernel 执行影响单步计算速度。三者一起决定了推理服务最终能承受多少并发。

14.6 适当使用“对比”让学生理解

技术讲义中应多使用对比，因为对比能帮助学生建立边界。

推荐对比方式：

Data Parallel 关注的是“同一个模型，处理不同数据”；
Tensor Parallel 关注的是“同一层模型，被多张 GPU 一起计算”；
Pipeline Parallel 关注的是“模型的不同层，放在不同 GPU 上顺序执行”。

这种写法比单独定义三个概念更清楚。

再比如：

Prefill 阶段的主要问题是一次性处理长输入，计算量大；
Decode 阶段的主要问题是一步一步生成，单步计算小，但调度和访存压力大。
14.7 多写“容易踩坑”的解释

讲义里要加入常见误区，因为这比单纯讲正确概念更容易让学生理解。

示例：

一个常见误解是：batch size 越大，推理一定越快。这个说法只对一部分指标成立。batch size 增大后，GPU 利用率可能提高，系统吞吐可能上升；但单个请求的等待时间也可能变长，KV Cache 显存占用也会增加。因此在在线服务中，batch size 不是越大越好，而是在吞吐、延迟和显存之间做权衡。

这种写法比直接说“需要权衡”更清楚。

14.8 避免“AI 味”的生动表达

不要为了生动而使用空泛修辞。

禁止写法：

“KV Cache 是大模型推理的记忆中枢。”
“Continuous Batching 让 GPU 火力全开。”
“Tensor Parallel 打破了单卡算力的天花板。”
“vLLM 重新定义了大模型推理。”
“SGLang 为高性能推理注入强大动能。”

这些表述看起来生动，但技术含量低，容易像广告。

推荐写法：

“KV Cache 保存的是注意力层中的 Key 和 Value 张量，不是语义记忆。”
“Continuous Batching 的核心作用是减少 decode 阶段的 GPU 空转。”
“Tensor Parallel 可以降低单卡显存压力，但会增加跨卡通信。”
“vLLM 的 PagedAttention 重点解决 KV Cache 的显存管理问题。”
“SGLang 更强调面向 LLM 程序的执行和调度优化。”
