# 课程重构执行规范

> 本规范给后续 agent 批量重构课程使用。当前样板课是 `labs/l20_vllm_scheduler_kv`。后续课程应对齐 L20 的组织方式：**先讲清楚系统问题和知识链路，再带读源码，最后用 lab / patch 做少量验收**。

## 1. 样板课

以 L20 为基准，先完整阅读这些文件：

| 类型 | 文件 |
|---|---|
| 课程入口 | `labs/l20_vllm_scheduler_kv/README.md` |
| 系统地图 | `labs/l20_vllm_scheduler_kv/system_map.md` |
| 主讲义 | `labs/l20_vllm_scheduler_kv/lecture.md` |
| 源码带读讲义 | `labs/l20_vllm_scheduler_kv/source_walkthrough.md` |
| 课后产物 | `labs/l20_vllm_scheduler_kv/outputs/` |
| 页面配置 | `quests/l20_vllm_scheduler_kv.yaml` |
| Quiz 配置 | `labs/l20_vllm_scheduler_kv/quiz.yaml` |

重构其他课程时，不要只模仿文件名，要模仿 L20 的教学逻辑：问题进入、系统定位、知识串联、源码落点、lab 验收、课后可复用产物。

## 2. 总体原则

每节课采用 lecture-first 结构。lab 是验收方式，不能成为讲授主体。

一节课应回答清楚：

1. 这节课解决哪个真实 AI Infra 问题。
2. 它在训练、推理、数据、RL、观测或多模态系统中的位置。
3. 学生为什么需要学它，不学会在真实系统里遇到什么问题。
4. 关键概念如何按因果关系串起来。
5. 真实源码里哪些文件、哪些行体现了这些机制。
6. lab 只验收哪一个最小合同。
7. 学完后留下什么可复用排查材料。

推荐节奏：

```text
70% 讲授：问题、概念、机制、系统位置、源码主路径
20% 演示：notebook / drill / mini_infra 现象
10% lab：实现最小 patch，跑测试验收
```

## 3. 每节课必须具备的文件

每个 lab 目录建议补齐以下文件：

```text
labs/<lab>/
├── README.md
├── system_map.md
├── lecture.md
├── source_walkthrough.md
├── outputs/
│   ├── README.md
│   ├── debug_checklist.md
│   ├── source_reading_card.md
│   └── <domain>_metrics_template.md
├── quiz.yaml
└── patch/
    ├── task.md
    ├── starter/
    ├── reference/
    └── tests/
```

如果某节课不适合 metrics template，可以换成同等用途的复盘模板，例如 `training_step_template.md`、`checkpoint_debug_template.md`、`rl_rollout_template.md`。

## 4. README 要求

`README.md` 是课程导航入口，不再只写 patch 命令。

必须包含：

- 本讲一句话定位。
- 学习路线：`system_map.md -> lecture.md -> source_walkthrough.md -> notebook -> quiz -> patch -> drill -> outputs`。
- 本讲属于哪条主线。
- 学完后能做什么。
- patch 命令和 drill 命令。
- 课后产物列表。

写法参考 `labs/l20_vllm_scheduler_kv/README.md`。

## 5. system_map.md 要求

`system_map.md` 负责给学生整体感。它要回答“这节课在全局系统里的位置”。

必须包含：

1. 所属章节的全局路线图。
2. 本讲局部系统图。
3. 概念依赖图。
4. 本讲和 lab 的关系。
5. 易混点表。
6. 本讲结束后的能力标准。

系统图可以先用 ASCII 图，重点是模块边界和数据/控制流，不追求美术效果。

## 6. lecture.md 要求

`lecture.md` 是主讲义。它应该像有经验的老师在讲课，逻辑自然，逐层推进。

不要把 `lecture.md` 写成固定模板填空。不同课程的知识形态不一样：有的课适合从线上事故切入，有的课适合先画系统图，有的课适合从一个最小例子推到真实框架。标题和小节数量可以因课置宜。

建议遵循下面的组织思路：

- 开头先说明这节课解决什么真实问题，以及学完能做什么。
- 尽早交代它在完整系统里的位置，让学生知道自己正在学哪一层。
- 按因果关系讲核心知识点，先讲必要概念，再讲机制如何运转。
- 适时引入 MiniInfra 或最小例子，帮助学生看见机制的简化形态。
- 再进入真实框架，解释真实源码为什么多了这些生产复杂度。
- 明确 lab 只验收哪一个最小合同，避免学生把 lab 当成课程全部。
- 如果有 drill、benchmark 或工单，说明指标怎么看、问题怎么排查。
- 结尾给一个简短小结，把本讲的知识链路收回来。

可以用 L20 的结构作参考，但不要机械复制。只要讲义能把“问题 → 系统位置 → 核心机制 → 源码落点 → lab 验收 → 生产排查”讲顺，就可以根据主题调整顺序和篇幅。

讲解要求：

- 每个知识点都要说明定义、直觉、输入、中间状态、输出、代价和边界。
- 概念之间要有因果关系，不能堆词条。
- 先讲问题，再讲机制，再讲源码，再讲 lab。
- 性能相关表述必须说明指标、比较对象、测试条件、优化原因和代价。
- 语言要清楚、具体、克制，像老师讲课，避免营销口吻。

禁止或尽量避免的句式：

- “随着……快速发展”
- “具有重要意义”
- “发挥着至关重要的作用”
- “赋能”
- “全面提升”
- “本文将深入探讨”
- “综上所述”
- “不是，而是”
- “不仅……而且……”

## 7. source_walkthrough.md 要求

`source_walkthrough.md` 是源码带读讲义，面向第一次读真实框架源码的学生。

必须包含：

1. 源码地图。
2. 按调用链排序的阅读步骤。
3. 每个文件只看哪些函数或字段。
4. 哪些分支可以先跳过。
5. 每一步读完要得到什么结论。
6. 读完后的自检问题。

注意：`source_walkthrough.md` 是讲义文档，应该通过 `lesson_docs` 在 app 里直接渲染。不要把它放进 `source_reading` 或 `lesson.source_refs`。

## 8. outputs 要求

每节课完成后，学生要带走可复用材料。`outputs/` 至少包含：

| 文件 | 作用 |
|---|---|
| `README.md` | 说明本目录产物怎么用 |
| `debug_checklist.md` | 面向真实问题的排查顺序 |
| `source_reading_card.md` | 复习源码主路径 |
| 模板文件 | 指标复盘、训练复盘、服务复盘或 RL 复盘 |

产物要能脱离课堂使用。不要写成“完成作业后提交报告”。

## 9. quests YAML 要求

每节课的 `quests/<lab>.yaml` 必须区分三类内容。

### 9.1 讲义文档

讲义类 Markdown 放到 `lesson_docs`：

```yaml
lesson_docs:
  - title: 系统地图
    path: labs/<lab>/system_map.md
    description: 本讲在章节中的位置、局部系统图、概念依赖和易混点。
  - title: 主讲义
    path: labs/<lab>/lecture.md
    description: 从真实问题、核心机制、源码抽象讲到生产排查。
  - title: 源码带读讲义
    path: labs/<lab>/source_walkthrough.md
    description: 按主路径组织的读源码路线。
```

`lesson_docs` 会在 app 的“本关讲义”里直接用 Markdown 渲染。讲义类 `.md` 不要放进 `source_reading`，也不要放进 `lesson.sections[].source_refs`。

### 9.2 源码阅读

`source_reading` 只放真正的源码文件，例如 `.py`、`.cu`、`.cpp`、`.ts`、`.tsx`。不要放 `.md`。

推荐格式：

```yaml
source_reading:
  - title: MiniInfra Scheduler
    repo_path: mini_infra/.../scheduler.py
    focus: waiting/running/finished、admission、decode、finished 释放
    highlights:
      - title: admission 双门
        lines: [46, 57]
        note: |
          - L46: waiting 非空且 running 未满时才尝试 admit。
          - L47: 先看队首请求，资源不足时不会丢掉它。
          - L48: 用 prompt token 数估算 KV block 需求。
```

### 9.3 页面讲义小节

`lesson.sections` 是 app 里的讲义摘要和源码穿插。它不需要复制完整 `lecture.md`，但必须和主讲义逻辑一致。

每个小节建议包含：

- `title`
- `plain_explanation`
- `mental_model`
- `why_it_matters`
- `source_refs`，只放源码文件
- `common_confusions`
- `checkpoint_questions`

## 10. 源码阅读卡片要求

源码卡片必须精简、准确、逐行讲解。

硬性要求：

- `source_refs.repo_path` 不允许是 `.md`。
- 每个源码片段通常 2 到 10 行。
- 单个片段最多 13 行；超过就拆成多个片段。
- 避免把大段函数整体塞进源码卡。
- 避免包含大量空行、注释块和无关分支。
- 注解必须精确到行，用 `Lxx:` 或 `Lxx-Lyy:` 开头。
- 每条注解说明这一行在机制中的作用。

推荐写法：

```yaml
source_refs:
  - repo_path: mini_infra/vllm/v1/core/sched/scheduler.py
    lines: [46, 57]
    title: MiniInfra Scheduler admission
    note: |
      - L46: waiting 非空且 running 未满时才尝试 admit。
      - L47: 先看队首请求，资源不足时不会丢掉它。
      - L48: 用 prompt token 数估算 KV block 需求。
      - L49-L54: KV 分配失败就停止 admit，请求继续留在 waiting。
      - L55-L57: 分配成功后，请求从 waiting 进入 running。
```

避免写法：

```yaml
note: |
  这段代码展示了 scheduler 的核心逻辑。
```

这种注解没有告诉学生每一行在做什么。

## 11. quiz.yaml 要求

Quiz 的前置项要和 app 渲染方式一致。

讲义类 Markdown 用 `kind: doc`，跳到 `#lesson`：

```yaml
- title: 读主讲义
  kind: doc
  path: labs/<lab>/lecture.md
  href: "#lesson"
```

patch/task.md 用 `kind: task`，跳到 `#patch`：

```yaml
- title: 最后读 patch/task.md
  kind: task
  path: labs/<lab>/patch/task.md
  href: "#patch"
```

源码文件用 `kind: source`：

```yaml
- title: 对照真实框架源码
  kind: source
  path: github_repo/<framework>/...
```

Quiz 题目只检查讲义讲过的关键概念。不要考没有讲过的源码细节。

## 12. 迁移步骤

后续 agent 重构单节课时按这个顺序执行：

1. 阅读现有 `README.md`、`patch/task.md`、`quiz.yaml`、`quests/<lab>.yaml`。
2. 找出这节课对应的真实系统问题。
3. 写 `system_map.md`。
4. 写 `lecture.md`。
5. 写 `source_walkthrough.md`。
6. 补 `outputs/`。
7. 更新 `README.md` 为课程导航。
8. 更新 `quests/<lab>.yaml`：
   - 加 `lesson_docs`
   - 精简 `source_reading`
   - 重写 `lesson.sections`
   - 源码片段逐行注解
9. 更新 `quiz.yaml`：
   - `doc` 指向 `#lesson`
   - `task` 指向 `#patch`
   - `source` 只指源码
10. 做验收检查。

## 13. 验收检查

每节课重构完成后必须检查：

```bash
python - <<'PY'
from pathlib import Path
import yaml

lab = "<lab_id>"
quest = yaml.safe_load(Path(f"quests/{lab}.yaml").read_text(encoding="utf-8"))
quiz = yaml.safe_load(Path(f"labs/{lab}/quiz.yaml").read_text(encoding="utf-8"))

assert quest.get("lesson_docs"), "missing lesson_docs"

for item in quest.get("source_reading", []):
    assert not item["repo_path"].endswith(".md"), item["repo_path"]

for section in quest.get("lesson", {}).get("sections", []):
    for ref in section.get("source_refs", []) or []:
        path = ref["repo_path"]
        assert not path.endswith(".md"), path
        lines = ref.get("lines")
        if isinstance(lines, list):
            assert lines[1] - lines[0] + 1 <= 13, (path, lines)
        note = ref.get("note", "")
        assert "L" in note, f"line-level note missing: {path}"

for item in quiz.get("prereq_checklist", []):
    if item.get("path", "").endswith(".md") and item.get("kind") != "task":
        assert item.get("kind") == "doc", item

print("ok")
PY
```

前端检查：

```bash
npx tsc --noEmit
```

页面检查：

```bash
curl -I http://127.0.0.1:3000/missions/<lab_id>
```

如果页面中出现讲义 `.md` 被当成“源码穿插”或“源码阅读”，说明 `source_reading` 或 `source_refs` 配错了。

## 14. 最终标准

一节课合格的状态：

- 学生打开页面先看到讲义正文，而不是 patch 任务。
- 学生能先建立系统地图，再进入源码。
- 讲义把每个知识点讲清楚，并按逻辑串起来。
- 源码卡只展示关键代码，少空行，逐行注解。
- lab 只验收最小核心机制。
- 完成后有可复用 checklist、源码卡和复盘模板。
